## 1. 研究目标与贡献假设

### 1.1 目标

- AnyView（生成器 G_φ）和 OpenD4RT（重建器 R_θ）保持**各自独立的结构**，不共享 backbone 或特征，也不加大型 bridge。
- 两个模型各自保留**原生 GT 监督**。
- 两者只通过输入输出上的**跨视角 4D（几何/轨迹）约束**交互。
- 最终要求两个模型**单独推理**时，都在自己的原任务上获得收益。

### 1.2 交互方式

- **AnyView**：用跨视角几何/轨迹一致性构造奖励，做 RL 微调（GRPO 类），同时保留原生去噪监督。
  - 奖励计算不需要梯度穿过 OpenD4RT、VAE 或采样链。
- **OpenD4RT**：在原生数据上训练，同时使用**经过校验的**生成视角及其变换后的 GT 标签。
- **交替更新**：每一轮固定一方、更新另一方。下一轮使用更新后的搭档。
  - 用"换搭档"实验检验"更新后的搭档是否比原始搭档更有帮助"。
- **query 选择和相机轨迹选择**：作为后续研究模块，第一版只用简单基线。

### 1.3 贡献假设（都是 [假设]，不预设成立）

1. **H1**：在只有单目 4D GT、没有目标 RGB 的数据上，用"GT 轨迹在新视角下的几何奖励"加冻结的 OpenD4RT，可以提升 AnyView 在独立评测上的几何和运动一致性，而且不损害外观质量。
2. **H2**：经过校验的生成视角加上精确变换的 GT 标签，能让 OpenD4RT 在真实评测上的提升超过同等预算下的原生训练和 GT warp 增广。
3. **H3**：交替迭代时，更新后的搭档比原始搭档带来更大的收益，也就是双向协同。
4. **H4（后续）**：带误差归因的 query 选择和可学习性感知的相机选择，优于简单基线。

**主线**（2026-09-25 选定）：**H3**，即交替更新两个模型，用换搭档实验检验双向协同。

**后续可选模块**：第一版不实现，等 S1、S3 的结果出来后再决定是否加入。

- 按时间分段的 advantage（§3.5 末尾）；
- 带正确标签的编辑训练（§5.1）。

**当前优先级**：先做 S1（真实视频上的奖励是否合理），再做 S3（AnyView 的随机采样和 log-prob 重算是否正常）。

- S1 第一轮已完成，结果和下一步计划见 §6 S1 末尾。
- 本轮对 §3.5 的主要修改：奖励加入了局部系的位置项 e_loc，用来检查生成视频是否跟随目标相机。

文献调研和选题记录见 `.pipeline/docs/`。

**查新（2026-09-25）**：如果只有 H1 成立，项目会退化为单向的"用重建模型指导新视角生成"。这个方向已有下列工作：

| 工作 | 做法 | 与本项目的区别 |
|---|---|---|
| World-R1（2604.24764） | Flow-GRPO，冻结的 3D 基础模型给奖励 | 3D 奖励导致过拟合到静态刚性，只能每 100 步暂停 3D 奖励，改用动态提示训练（"周期解耦"），动态区域没有几何约束 |
| CamVerse（2512.02870） | 按片段比较相对位姿作为奖励 | 只约束相机，并且需要参考视频 |
| VIGOR（2603.16271） | 用 VGGT 计算重投影误差作为奖励 | 只衡量生成视频内部的一致性，没有外部 GT |
| MVTrack4Gen（2606.26087） | 用多视角点跟踪作为 4D 生成的监督 | 它是扩散模型内部的训练损失，不是用外部 critic 做 RL |

本项目的区分点：

- 奖励来自**外部 GT 4D 轨迹**，数据是没有目标 RGB 的单目数据；
- 奖励包含**动态位移项**；
- critic **双向更新**。

"重建与生成互促"方向的已有工作：

- GenFusion（2503.21219）和 Vivid4D（2504.11092）限于逐场景优化；
- Ouroboros3D（2406.03184）、Gen3R（2601.04090）、JOG3R（2501.01409）把两个模型在架构上耦合或联合训练。

截至调研日期，没有找到前馈模型、架构解耦、并且两个模型都能单独推理的双向提升工作。

**[待核查]**：以上查新只做了一轮检索，结论没有经过独立核查，**不能据此认定查新已经完整**。

**已知不能保证的事项：**

- 不保证避免坍缩或合谋。
- 不能证明不存在奖励投机。
- 双向提升不必然成立。

## 2. 两类数据分支

| | NVS GT 分支 | D4RT GT 分支 |
|---|---|---|
| 数据 | 同步多视角 RGB 加相机（Kubric-5D） | 源视频加实际可用的深度、轨迹、相机（9Mix） |
| 缺少 | 几何 GT | 目标视角 RGB |
| AnyView 的原生监督 | 去噪损失，以真实 V_b 为目标 | 无（但训练中会穿插 Kubric 的原生监督） |
| 核心难点 | 可靠共视 query 的选择、跨视角对应、尺度 | 目标相机的选择、目标视角可见性、生成标签的可靠性 |
| 优先级 | 完整规划保留；等尺度和对应流程明确后再接入 | **最小原型优先** |

### 2.1 D4RT GT 分支（最小原型）

**更新 AnyView（OpenD4RT 冻结）：**

- **参考**：GT 世界轨迹 X_GT，按选定的 C_b 精确变换到目标相机坐标系。
- **奖励**：冻结的 R_θ 在生成视频 V̂_b 上、在 GT 预期投影位置处的轨迹误差，定义见 §3.5。
- **有效区域**：满足三个条件的点和时刻——GT 有效、在目标视角 z-buffer 中判定为可见、落在画面内。另外按 OpenD4RT 在真实源视频上的误差做门控。
- **更新对象**：只更新 AnyView 的 LoRA。
- **同时训练**：交替加入 Kubric-5D 的原生去噪损失。

**更新 OpenD4RT（AnyView 冻结，使用缓存的生成视频）：**

- **参考**：由 X_GT 和 C_b 精确计算出的原生 query 标签。
- **损失**：OpenD4RT 的原生损失，只在经过校验的区域上计算，与原生 9Mix 训练混合。详见 §5。

### 2.2 NVS GT 分支（完整规划，暂不实现）

**更新 AnyView：**

- **对应关系**：只在真实视频对 (V_a, V_b) 上，用冻结的 R_θ 建立，并且在看到生成视频之前就固定下来。具体步骤：
  1. 把 R(V_a) 的点投影到相机 b；
  2. 与 R(V_b) 做深度一致性检验；
  3. 做往返一致性检验：在投影位置查询 R(V_b)，再投回相机 a，应落回原像素附近；
  4. 通过的点构成可靠的共视对应。
- **奖励**：R(V̂_b) 在这些对应的预期投影位置上的轨迹误差。
- **原生去噪损失**：保留，以 V_b 为目标。
- **辅助项或基线**：同相机的 R(V_b)↔R(V̂_b) 比较，以及相对 V_b 的 LPIPS 锚定。它们**不替代**跨视角奖励。
- **注意**："同相机同像素"不等于同一个物理点，物理点的对应要由跨视角几何决定。

**更新 OpenD4RT：**

| 交互 | 判断 | 条件 |
|---|---|---|
| 真实视频对 R(V_a)↔R(V_b) 的跨视角一致性（相机已知） | 可行 | 与 AnyView 无关，属于普通自监督，作为对照 |
| 在 V̂_b 上训练，伪标签来自真实视频对，只用生成与真实一致的区域 | 有条件可行 | 这一分支有 V_b，可以不经过 OpenD4RT、直接做局部校验。预期主要提升 OpenD4RT 在生成视频上的鲁棒性，也就是作为 critic 的质量；对真实视频单独推理的收益是 [假设] |
| 不校验生成视频就用 R(V_a)↔R(V̂_b) 更新 OpenD4RT | 不采用 | 会让 OpenD4RT 学着附和生成出来的内容 |

**尺度估计有两种方案**：

- **方案 A**：每段视频用自身的相机运动估计。把 OpenD4RT 的查询结果做 Umeyama 对齐，得到它自己的相机轨迹，再用它的平移与已知的相机平移做最小二乘。
- **方案 B**：在 (s_a, s_b/s_a) 的对数网格上做一致性搜索，取通过投影一致性检验的点数最多的一组尺度。

两种方案的对应关系都是估计的输出而不是输入，所以不存在"先用尺度建对应、再用对应估尺度"的循环。

**退化情况的处理**：

- 小基线或纯旋转时，只能确定两段视频的尺度比 s_b/s_a，放弃绝对位置项。
- 退化判据用中位视差角，阈值 [待定]。
- Kubric-5D 的外参不是米制（`metadata.json` 中 `extrinsics.metric: false`），但 16 个相机之间是一致的。

## 3. 接口与数学定义

### 3.1 已确认的接口事实

**OpenD4RT 的时间与输入**

- **时间索引是离散的** [代码确认]：
  - `OD/src/model/query_embedding.py:61-63` 使用 `nn.Embedding(48)`；
  - `:77-78` 把越界索引**悄悄截断**，不会报错；
  - `OD/src/model/d4rt.py:271-273` 把索引转成 `.long()`；
  - 所以不支持小数时间，也不能输入外部相机。
- **48 帧是训练配置，不是结构硬上限** [代码确认]：
  - 帧数配置在 `OD/checkpoints/*/model.yaml:7`；
  - 位置编码按展平后的 token 序号做一维正弦编码（`OD/src/model/encoder.py:122`），与帧数 T 无关；
  - 但 48×256²/(2·16·16) = 6144，正好等于 `max_tokens`（`model.yaml:25`），更多帧会触发空间平均池化（`encoder.py:101-110`）。
- **奇数帧会丢最后一帧** [代码确认]：
  - 时间方向的 patch 大小为 2，步长也是 2（`encoder.py:75-78`），41 帧时最后一帧不进入编码器；
  - 局部 RGB patch 从 t_src 帧上取（`query_embedding.py:92,110`）。
- **训练时的帧间隔** [代码确认]：
  - 只有 1 或 2（`OD/configs/train_effective.yaml:201-202`，`OD/src/data/raw_augment.py:264`）；
  - 只有场景太短时，才重复最后一帧补齐（`raw_augment.py:247`）。
- **xyz 输出没有尺度** [代码确认]：
  - `OD/src/losses/d4rt_loss.py:18-26` 把预测和 GT 各自除以平均深度；
  - 由 `train_effective.yaml:144` 开启；
  - 评测时用 Umeyama Sim3 对齐（`OD/src/eval/tasks.py:11`）。
- **冻结当 critic 时必须用 `eval()`**：编码器和解码器都有 dropout=0.1（`encoder.py:88`）。

**OpenD4RT 的 query 语义** [代码确认]：

| 字段 | 实际含义 | 代码位置 |
|---|---|---|
| `t_cam` | 输入视频自身第 t_cam 帧的相机，定义坐标系 | — |
| `xyz_3d` | 点在 t_tgt 时刻的位置，表达在 t_cam 帧相机坐标系下 | `OD/src/data/depth_query_builder.py:211,481` |
| `uv_2d` | 投影到 **t_tgt** 帧视角，而不是 t_cam 帧 | `depth_query_builder.py:246,497`；`d4rt_loss.py:133-147` |
| visibility | 在 t_tgt 帧视角下的可见性 | 同上 |
| `displacement` | P(t_tgt) − P(t_src)，旋转到 t_cam 帧坐标系 | — |

**AnyView 的帧数与相机** [代码确认]：

- 只支持 1+4k 帧，最多 41 帧（`AV/anyview/vae.py:13,62`，`AV/anyview/cameras.py:215`）。
- world2cam 满足 x_cam = R x_world + t（`cameras.py:14`）。
- 所有位姿都重新锚定到目标视角第 0 帧（`AV/scripts/infer.py:132`，`cameras.py:91`）。
- 相机 cross 通道要乘一个按数据集查表的尺度因子（`cameras.py:29-49`），查不到会报错（`:67`）。

**Kubric-5D** [代码确认]：

- `metadata.json` 的 labels 里列了 depth，但实际文件只有 `rgb/` 和 `lowdim/`，没有深度。
- 外参 `metric: false`；AnyView 对它用 1/32 的尺度因子（`AV/anyview/kubric_dataset.py:12`）。
- 只使用第 0 帧的内参（`kubric_dataset.py:65-66`）。
- 相机轴向：抽查 cam00 第 0 帧，+z 轴指向场景中心，推测是 OpenCV 约定（+x 右、+y 下、+z 前），与 OpenD4RT 的数据规范一致。**[待核查]**：需要用投影单元测试确认。

### 3.2 相机约定与坐标变换 [设计]

- **统一约定**：OpenCV 相机坐标（+x 右、+y 下、+z 前），相机到世界为 `X_w = R_t X_c + c_t`，等价于 `T_wc(t) = [R_t | c_t]`。
- **两套坐标的换算**：
  - AnyView 的 world2cam 是**重新锚定到目标视角第 0 帧之后**的结果。它求逆得到的是"相机到锚定后世界坐标"的变换，**不是**数据集原始世界坐标下的 `T_wc`。
  - 只有两者使用同一个世界坐标系时，才满足 `T_wc = inv(world2cam)`。
- **实现约定**：
  - 奖励、GT 变换、z-buffer 一律使用数据集**原始**世界坐标下的相机 `T_wc`。
  - AnyView 的条件输入单独使用重新锚定后的相机。
  - 重新锚定时的变换 `T_anchor`（原始世界坐标 → 锚定后世界坐标）要显式保存，以便单元测试核对：`world2cam_anchored = inv(T_wc) · inv(T_anchor)`。
  - [待核查]：以 `AV/anyview/cameras.py:91` 的实际实现为准。
- **需要单元测试的内容 [待核查]**：
  1. 用 C_a 把 GT 点投影到 V_a，检查是否落在对应像素上；
  2. 两边的内参缩放约定：AnyView 的 `scale_intrinsics` 直接乘以 new/orig（`cameras.py:109-126`），像素网格是 0..W−1；OpenD4RT 用 u/(W−1) 归一化。二者可能相差 0.5 像素。

### 3.3 内参缩放

- **AnyView 输入**：用 `snap_shape` 缩放到 576 网格，内参按 `scale_intrinsics` 缩放 [代码确认]。
- **OpenD4RT 输入**：缩放到 256×256，宽高比 token 取 W/H，缩放方式与 `OD/infer_track_3d.py:37-43` 一致。
  - 奖励里的投影统一在 256² 分辨率上计算；
  - 查询坐标用 `u = x/(W−1)`、`v = y/(H−1)`；
  - K 的缩放约定以投影单元测试的结果为准。

### 3.4 帧数与时间对齐 [设计 + 假设]

- AnyView 生成 **41 帧**。交互时只把**前 40 帧**送给 OpenD4RT。
  - 这是候选方案，需要按 §6 S1 的共同时间点对照来验证。
- OpenD4RT 的原生训练仍然用 **48 帧**。
- 源视频和生成视频逐帧同步；从源数据取帧时，帧间隔选 1 或 2。
- 不采用"41 帧分散重复成 48 帧"。原因：重复帧会在时间 patch 内造成零运动，帧间隔也不再均匀，与 OpenD4RT 训练时的分布不一致。
- **40 帧与 48 帧的 clip 分开组成 microbatch**：
  - 各自前向，按权重累积梯度；
  - 不为了混进同一个 batch 而补帧。

### 3.5 尺度、位置误差与位移误差 [设计]

**奖励由两组查询组成**，它们共享锚点、V、尺度 s 和上限 c：

- **t₀ 系的项**（位置 e 和位移 d）：固定 t_cam = t₀，把整条轨迹放在同一个坐标系下，用来检查动态轨迹。
- **局部系的项**（e_loc，见下文）：t_cam = t，用来检查生成视频是否跟随目标相机 C_b。

**为什么需要局部系的项**（S1 结果，2026-09-25）：

- 在 t₀ 系中，静态点的参考值 Y(i,t) 不随时间变化，也与相机轨迹无关。所以只用 t₀ 系的项时，"不跟随 C_b 的静止视频"在静态点上不会受惩罚。
- S1 用"第 0 帧重复 40 次"的冻结视频检验。在一个没有动态点、相机移动 1.8 m 的片段上，冻结视频的奖励甚至**高于**真实视频。

- 对锚点 i（在源视频 t₀ 时刻），查询：
  ```
  u, v   = π_b(X_GT(i, t₀)) / (W−1, H−1)
  t_src  = t₀,   t_tgt = t,   t_cam = t₀
  ```
- OpenD4RT 的输出是 X̂_c(i,t)，位于相机 b 的 t₀ 帧坐标系下，尺度未知。
- **参考值**（在相机 b 的 t₀ 帧坐标系下）：
  ```
  Y(i,t) = R_b(t₀)ᵀ (X_GT(i,t) − c_b(t₀))
  ```
- **尺度只作用于相机坐标，然后再用已知外参变换到世界坐标**：
  ```
  X̂_w(i,t) = R_b(t₀) (s · X̂_c(i,t)) + c_b(t₀)
  ```
  相机平移不参与缩放。旋转不改变长度，所以下面的误差可以直接在相机坐标下计算。
- **尺度估计器**：取深度比的中位数。这只是一个估计器，不是任意鲁棒目标的闭式解。
  - 只用**锚点时刻 t₀** 的点拟合尺度。在 t₀，锚点在相机 b 中可见，深度必然为正。
  - 之后的时刻不参与拟合：轨迹表达在固定的 t₀ 相机坐标系下，物体可能移动到这个相机平面的后方（z < 0），同时仍被当前时刻的相机看到。
  - 先定义两个集合：
    - **Q₀**：固定的锚点集合，只由 GT 决定，所有候选共用；
    - **V⁺**：Q₀ 中预测适合做尺度拟合的子集。
  ```
  Q₀ = {i : (i,t₀) ∈ V, Y_z(i,t₀) > z_min}
  V⁺ = {i ∈ Q₀ : X̂(i,t₀) 有限, X̂_z(i,t₀) > z_min}
  s  = median_{V⁺} ( Y_z(i,t₀) / X̂_z(i,t₀) )
  ```
  - **尺度无效**：|V⁺| < max(N_min, κ·|Q₀|)，或者 s 不是有限正数。这时该候选按最大惩罚计分，即 r = −c·(w_p + w_d·1[|V_d| > 0] + w_loc·1[|V_loc| > 0])，并记录下来。
  - V⁺ 与 Q₀ 都按锚点计数，口径一致；不要拿锚点数去和 |V| 比较，|V| 计的是"点 × 时刻"。
  - 如果一组中大多数候选的尺度都无效，跳过这一组。
  - z_min、N_min、κ 均为 [待定]。
- **归一化**：每个锚点的深度 z̄_i = max(Y_z(i, t₀), z_min)。
- **位置误差和位移误差使用同一个 s**：
  ```
  e(i,t) = min( c, ‖ s·X̂_c(i,t) − Y(i,t) ‖ / z̄_i )
  d(i,t) = min( c, ‖ s·(X̂_c(i,t) − X̂_c(i,t₀)) − (Y(i,t) − Y(i,t₀)) ‖ / z̄_i )
  ```
  - **预测无效**：出现以下任一情况时，e 和 d 都记为 c，不从分母中去掉：
    - 输出不是有限值；
    - 在锚点时刻 t₀，X̂_z(i,t₀) ≤ z_min。
  - **t ≠ t₀ 时，不因固定参考坐标系下 z 为负而惩罚。**
- **有效集 V 与模型输出无关**：
  - V 只由三个条件决定：GT 有效、预先确定的目标视角可见性（z-buffer 的"可见"状态）、落在画面内。
  - V 在看到生成视频之前就确定，同组所有候选共用。
  - 预测不是有限值时，V 不变，对应的误差记为上限 c。否则，生成失败的候选可以通过减少参与评分的点来降低惩罚。
  - 位移项的集合 V_d = {(i,t) ∈ V : t ≠ t₀, (i,t₀) ∈ V}，同样只由 GT 决定。
  - **|V_d| = 0 时禁用位移项**：这时 r 只含位置项，避免对空集除以 0。
- **局部系的位置项 e_loc**：检查生成视频是否跟随 C_b。
  - 同一批锚点的另一组查询：
    ```
    u, v = π_b(X_GT(i, t₀)) / (W−1, H−1)
    t_src = t₀,   t_tgt = t,   t_cam = t
    ```
  - OpenD4RT 的输出记为 X̂_loc(i,t)，位于相机 b 的 t 帧坐标系下。
  - 参考值：`Y_loc(i,t) = R_b(t)ᵀ (X_GT(i,t) − c_b(t))`。
  - 误差：沿用 t₀ 系中拟合出的尺度 s 和归一化深度 z̄_i，不重新拟合：
    ```
    e_loc(i,t) = min( c, ‖ s·X̂_loc(i,t) − Y_loc(i,t) ‖ / z̄_i )
    ```
    t = t₀ 时，两组查询完全相同，所以局部项只在 t ≠ t₀ 时计算。
  - 集合：V_loc = {(i,t) ∈ V : t ≠ t₀}，只由 GT 决定。V 要求点在 C_b(t) 下可见，所以 Y_loc 的 z 必然为正。
  - 无效预测的处理与 e 相同：输出不是有限值，或锚点在 t₀ 无效时，记为 c。
  - |V_loc| = 0 时禁用局部项。
  - 代价：查询数翻倍，但视频编码只需一次，两组查询共用编码结果。
- **暂不加入**组内的尺度一致性惩罚。
- **第一版的奖励形式**：标量 r（§7.2），经组内标准化得到 advantage（§4.4）。所有去噪步共用这一个 advantage。
- **不采用"周期解耦"**（World-R1 做法：定期暂停几何奖励、只用动态提示训练）。动态区域由 d 项监督。
  - [假设]：这样就足以避免过拟合到静态刚性。
  - 检验方法：比较动态程度（例如 VBench 的 dynamic degree），并检查模型是否退化成生成近乎静止的视频。
- **后续可选模块：按时间分段的 advantage [设计]**，作为消融实验，不作为区分度的依据。
  - 做法：把 r 拆成每个时刻的分项 r(t)，每个分项在组内单独标准化后再汇总。
  - 它与标量 r 的组内标准化**优化的权重不同**。
  - 视频的时间分段**不等于**扩散去噪步上的信用分配。如果所有去噪步仍共用同一个汇总后的 advantage，分段的作用主要是改变各视频时刻的权重。
  - 方差小的时刻，标准化会放大其中的噪声。

**每个候选单独拟合 s 的已知盲区：**

1. 整体深度按同一比例偏大或偏小时，会被 s 完全吸收，得不到惩罚。
2. 生成视频隐含的相机平移幅度不对时，只能部分体现在误差里，能体现多少取决于 OpenD4RT 如何理解视差。[假设]
3. t₀ 系的项**不检查相机跟随**。静态点的参考值与相机轨迹无关，冻结视频能拿到接近甚至超过真实视频的分数（S1 已验证）。相机跟随完全由局部项 e_loc 负责。e_loc 中会混入 OpenD4RT 自身的位姿估计误差。参考数据（stride 2，30 段真实视频）：全部改用局部系计算时，噪声底为 −0.140，t₀ 系为 −0.128。组合奖励的噪声底见 S1 结果。

### 3.6 对应关系的近似

奖励只衡量**"物理点在预期投影位置上的几何"**，不保证生成视频在这个像素上仍然是同一个点。

已知的失效情况：

| 失效情况 | 能否被发现 |
|---|---|
| 小物体被删除，背景深度接近 | 可能漏检 |
| 物体沿深度相近的方向平移 | 可能漏检 |
| 两个相似物体互换 | 只有两者运动不同时，位移项才能发现 |
| 运动物体被换成静止背景 | 只有 query 里有足够的动态点时，位移项才能发现 |

这些情况要用 §6 S1 的人为退化测试来检查；测试只能发现一部分漏洞。

## 4. AnyView 的 RL 实现规划 [设计]

### 4.1 参数化 [代码确认]

- **缩放系数**：`AV/anyview/vendor/denoiser_scaling.py:31-34`：τ = σ/(1+σ)，c_skip = 1−τ，c_out = −τ，c_in = 1−τ。
- **状态**：VE 形式 x = x₀ + σε（`AV/scripts/train_dvs.py:170`）。
- **换算到 rectified flow**：令 z = x/(1+σ)，得到 z = (1−τ)x₀ + τε，并且 x̂₀ = z − τF（`AV/anyview/pipe.py:171`）。
  - 所以网络原始输出 F 就是 rectified flow 的速度 v̂ = ε − x₀。
  - 这与 Flow-GRPO 的约定一致：它的 sigma 对应这里的 τ，它的 model_output 对应这里的 F。
- **噪声调度**：σ ∈ [0.002, 80]，Karras ρ=7，共 35 步（`pipe.py:21`，`AV/anyview/config.py`）。
  - 对应的 τ_max = 80/81 < 1，不存在 τ = 1 处的奇点。
- **现有采样器是确定性的**：
  - 第一步用 Euler（`AV/anyview/vendor/rectified_flow_scheduler.py:131`）；
  - 之后用依赖上一步 x̂₀ 的 2 阶 Adams-Bashforth（AB2，`:139`）；
  - `:125` 的注释说明随机扰动（churn）没有实现，`:98` 的 `generator` 参数未被使用。
- **随机维度只包括 rgb0**：
  - 只有 rgb0 是输出（`AV/anyview/logistics.py:78`）；
  - v1 流和两路 cams 通道每一步都被条件输入覆盖（`logistics.py:135`，`pipe.py:175,284`）；
  - 384×576、41 帧时，D = 16×11×48×72 ≈ 6.1×10⁵。
- **同组候选靠 seed 区分**：初始噪声由 `arch_invariant_rand(seed*100+v)` 生成（`pipe.py:244-248`）。
- **训练路径可微**：`pipe.denoise` 对 DiT 参数可微，`train_dvs.py:178` 已经这样用。
  - `generate`、VAE 解码、PIL 缩放都在 no_grad 下，但它们只出现在 rollout 和评分中。

### 4.2 随机转移（Flow-GRPO 式 SDE，在 z 坐标中计算）

- 时间方向：τ 递减，Δ_i = τ_{i+1} − τ_i < 0。
- 噪声系数：g_i = a·√(τ_i/(1−τ_i)) = a·√σ_i。
- 由高斯插值得到的 score：
  ```
  ∇log p_τ(z) = −(z + (1−τ)v̂)/τ
  ```
- 转移均值：
  ```
  μ_θ     = z_i + [ v̂ + (g_i²/(2τ_i)) (z_i + (1−τ_i) v̂) ] Δ_i
  ```
- 下一状态：
  ```
  z_{i+1} = μ_θ + g_i √(−Δ_i) ξ,   ξ ~ N(0, I_D)
  ```
- 与参考实现 `flow_grpo/diffusers_patch/sd3_sde_with_logprob.py:50-68` 逐项对应。
- x = (1+σ)z 与 z 之间只差一个与 θ 无关的常数雅可比，所以统一在 z 坐标下计算 log-prob。
- **随机性只作用于 rgb0 通道**，条件通道保持和释放版一致的确定性处理。
- **端点处理**：
  - 初始状态沿用 x = 80ε，即 z ≈ 0.988ε；
  - 最后一步转移之后，释放版在 σ_min 处还会做一次确定性的 x̂₀ 计算（`pipe.py:278-281`），不计入 log-prob，奖励就在这一次的输出上计算。
- **噪声量级（实算，a = 0.7、35 步）**：
  - 每步噪声 g√(−Δ)：σ > 10 时为 0.285–0.308；σ < 0.1 的第一步为 0.033，之后降到 0.03 以下（`anyd4rt/tests/test_sde.py` 实算）；
  - 修正项系数 g²(−Δ)/(2τ) 的最大值为 0.0523。
  - 这只说明单步不会数值爆炸；整条链的生成质量需要实测。
- **a = 0 只用于检查确定性转移**：此时 μ 应精确复现 Euler 采样。零方差高斯没有有效的 log-prob，所以不计算。
- **与 AB2 的关系**：AB2 依赖上一步的 x̂₀，不能用在随机步上。
  - 混合窗口的做法：窗口内随机、窗口外确定性，窗口外可以继续用 AB2。这是第二阶段的选项，参考 MixGRPO 和 RL3DEdit 的窗口大小 4。
  - 必须先通过 §6 S3 的质量验证。
- **数值精度**：log-prob、概率比和 KL 一律用 **FP32** 计算。参考实现也是先转成 float 再计算（`sd3_sde_with_logprob.py:36-40`）。

### 4.3 log-prob：联合与按维度平均

- **联合 log-prob（精确）**：
  ```
  ℓ = Σ_d log N(z_{i+1,d}; μ_d, g_i²(−Δ_i))
  ```
- **按维度平均**：ℓ̄ = ℓ / D。参考实现就是这样做的（`sd3_sde_with_logprob.py:89`），并配合 clip 范围 1e-4（`flow_grpo/config/base.py:99`）。
- **两者定义的概率比不同**：exp(ℓ̄_θ − ℓ̄_old) 等于联合概率比的 1/D 次方。所以两者的信任域和 clipping 语义都不同，按维度平均**不只是**防止溢出。
- **严格同策略时**：按维度平均的梯度等于精确策略梯度乘以 1/D，只相当于换了学习率。
- **第一版的选择**：
  - 采用按维度平均，以便对照参考实现的超参数；
  - 每批 rollout 只做**一次**优化器更新，所以 clipping 不会被触发，同时记录 clipfrac；
  - 以后改成多次内循环时，重新确定 ε。
  - 注意：视频 latent 的维度 D 远大于图像，参考实现的 ε 不能直接照搬。

### 4.4 策略目标与 KL

- **advantage**：组内标准化，截断到 ±5。
  ```
  A_i = clip( (r_i − mean_g) / (std_g + 1e−4), −5, 5 )
  ```
  - 标准化方式对应 `flow_grpo/scripts/train_sd3.py:766` 和 `flow_grpo/stat_tracking.py`；截断上限来自 `config/base.py:97`。
  - 组内 std_g < δ 的组跳过，δ [待定]。
- **策略损失**（对应 `train_sd3.py:886-898`）：
  ```
  L_π = −mean_{i, j∈S} min( ρ_ij·A_i , clip(ρ_ij, 1−ε, 1+ε)·A_i )
  ρ_ij = exp( ℓ̄_θ − ℓ̄_old )
  ```
- **KL**：相对 LoRA 关闭的参考模型逐步计算。
  - 精确形式为同方差高斯之间的 KL：
    ```
    KL_j = ‖μ_θ − μ_ref‖² / (2 g_j²(−Δ_j))
    ```
    再按维度平均。
  - 参考实现（`train_sd3.py:900`）只除以 2g²，少了 (−Δ) 这个因子。**第一版用精确形式**，并在代码中注明。
  - 参考实现的默认 β = 0（`config/base.py:107`）；我们的 β 为 [待定] 的小正值。
- **AnyView 总目标**：
  ```
  L = L_π + β·L_KL        （D4RT GT 分支的 batch）
    + λ_nat·L_denoise     （Kubric-5D batch，原生损失见 train_dvs.py:153-189）
  ```
- **更新范围**：只训练 DiT 的 LoRA 参数。
  - LoRA 需要在自定义 DiT 上手写，不能直接套 peft；
  - [待核查]：与 DDP（`find_unused_parameters`）是否兼容，以及保存后能否被 `load_dit` 严格加载。

### 4.5 梯度与同策略约束

- **rollout 和评分**：不带梯度。包括采样、VAE 解码、缩放和 OpenD4RT 前向。
- **策略重算**：对保存下来的 (z_i, τ_i, z_{i+1})，用 x_i = (1+σ_i)z_i 加上条件通道，重跑一次 `pipe.denoise`，只对 LoRA 求梯度。
  - [待核查]：DiT 在 `.train()` 和 `.eval()` 下行为是否一致；bf16 下 rollout 与重算之间的数值偏差有多大。
- **严格同策略的条件**：从一次 rollout 开始，到这批 rollout 的策略梯度计算完成为止，**不能插入任何改变参数的更新**，包括 Kubric 原生监督的更新；否则不能再称为严格同策略。
  - Kubric 原生损失可以和策略损失放在**同一个优化器步**里，参数相同，所以仍是同策略；
  - 也可以放在两批 rollout 之间单独更新。

## 5. 用生成数据训练 OpenD4RT 的条件 [设计 + 假设]

- **GT 变换是精确的，不代表生成内容与标签相符。**
  - 标签由 X_GT 和我们自己选的 C_b 精确算出；
  - 但生成视频在对应像素上的内容可能是错的。
- **目标视角可见性来自源视角的 z-buffer，而它是不完整的**：
  - 做法：在每个时刻 t，把源视频第 t 帧的 GT 深度反投影、再投影到 C_b(t)，在 256² 分辨率上建 z-buffer。容差 max(0.05, 0.02z) 沿用 `depth_query_builder.py:259`。
  - 每个点的可见性分三种状态：
    - **可见**：没有已知的更近表面；可能因为源视角没看到遮挡物而判断错误。
    - **遮挡**：存在已知的更近表面。
    - **未知**：附近没有 z-buffer 覆盖。
  - **未知**状态不作为确定的 visibility 标签。
  - 目标相机的变化幅度保持适中，以减少漏掉的遮挡。
- **逐字段的监督掩码 [设计]**：
  - 所有字段先继承同一个**公共掩码**：`M_anchor = 锚点 GT 有效 ∧ M_ver`。其中 M_ver 是生成内容的校验掩码，定义见下文。
  - 每个字段再在 M_anchor 上叠加自己的 GT 有效条件。
  - 任何字段都**不能**绕过 M_anchor。例如 displacement 不能仅因为"两个时刻的 GT 都有效"就进入监督。

| 字段 | 标签 | 何时提供（都要求 M_anchor） |
|---|---|---|
| `xyz_3d` | GT 点在 cam_b(t_cam) 坐标系下的位置 | t_tgt 时刻的 GT 有效 |
| `uv_2d` | π_b(X_GT(t_tgt)) | t_tgt 时刻判定为可见 |
| visibility | 可见或遮挡 | 状态不是未知 |
| `displacement` | R_b(t_cam)ᵀ (X_GT(t_tgt) − X_GT(t_src)) | t_src 和 t_tgt 两个时刻的 GT 都有效 |
| `normal` | — | 不提供 |

  **[待核查]**：OpenD4RT 原生损失的各项掩码（`d4rt_loss.py`）能否直接接收这些字段级掩码；以及生成视频上 query 的采样方式，建议沿用原生的 t_src/t_tgt/t_cam 采样，只限定在有效锚点上。
- **校验掩码 M_ver 是启发式的，不证明标签正确。**
  - 做法：比较 V̂_b(π_b X) 与 V_a(π_a X) 附近 5×5 patch 的颜色，先做每段视频的颜色归一化，在 Lab 空间比较。要求在 t_src 以及大多数可见的 t_tgt 上，差异都小于 τ_ph。
  - 这个判断不经过 OpenD4RT；但会偏向纹理丰富的区域，而且在反光、无纹理的区域会失效。
  - 可选：只使用组内 reward 排名靠前的候选。
- **损失**：
  ```
  L = L_9Mix + β_g · L_D4RT(V̂_b ; 标签, M_ver)
  ```
  生成视频在 batch 中的比例 [待定]，初始可以取 10–20%。
- **必须做的公平对照（预算相同）**：
  1. 只用原生数据，训练相同的额外步数；
  2. 用 GT 深度前向 warp 源视频得到的伪新视角作增广（带空洞）；
  3. 生成视频加 M_ver 掩码。

  如果 (3) 不超过 (2)，就说明**当前配置未支持 H2**。

### 5.1 带正确标签的编辑训练（后续可选模块）[设计 + 假设]

**第一版不实现。** 要先把两类编辑分开：

**(a) 人为图像退化：只用于奖励诊断（S1）**

- 就是 S1 里的平移、交换、删除、冻结、模糊。
- 用途只有一个：检查奖励会不会给退化视频高分，也就是泄漏率。**不要求**得到编辑后的精确 GT，也**不用于训练**。
- 这类编辑得不到正确的几何标签，原因如下：
  - **冻结物体的像素区域，不等于物体在世界坐标中静止。** 相机运动时，静止物体在图像中的位置和外观仍会变化，所以"位移为 0、位置固定"不成立。
  - **图像中平移一个物体，不能直接给它的三维点加同一个平移量。** 深度、透视和遮挡都会改变。
  - **交换两个物体的图像区域，不能只交换轨迹。** 形状、深度、遮挡关系都会改变。

**(b) 带正确标签的编辑：可以用于训练**

只允许两类编辑：

1. **标签能严格推导的变换**：
   - 例如整段视频的空间裁剪或缩放，同时相应地修改内参；
   - 或者时间方向的抽帧、倒放，轨迹也相应地重排。
   - 这类变换不改变场景内容，只能检验 critic 对输入变换是否一致，不能检验它是否忠实于内容。
2. **在可控的三维场景中重新渲染**：
   - 例如在 Kubric 场景中移动或删除物体后重新渲染，GT 由渲染器直接给出。
   - [待核查]：Kubric-5D 或 kubric_full 是否提供可重新渲染的场景文件。

**不采用**"编辑视频、但标签保持原样"的训练，也不把它作为对照组。它会主动引入错误的监督，结果难以解释。

**损失（如果启用）**：

```
L = L_9Mix + β_e · L_D4RT(V_edit ; 正确标签)
```

**目的的表述**：这个模块只用于**检验能否降低 §3.6 中的相关失效**，不宣称它能防止合谋。

**验证**：

- S1 的泄漏率是否下降；
- S4 的 Kendall τ 是否上升；
- WorldTrack 上是否掉点。

设置：

- **整体适用范围**：
  - 只有一个数据集（PointOdyssey，合成数据）、一个权重、60 段；
  - 只测了 C_b = C_a，也就是把真实视频当作"生成结果"；
  - 奖励参数都是占位值。
  - 以下结论都不能直接推广到 C_b ≠ C_a 的生成视频上。

结论：

- **投影约定正确**：
  - PointOdyssey 的 `extrinsics` 是 OpenCV 约定的 T_cw；
  - 用 K 投影 `trajs_3d`，与 `trajs_2d` 的偏差中位数为 0.14 px。
- **40 帧与 48 帧输入的对照（§3.4）**：在共同时间点 t ∈ [0, 39] 上，用同样的查询比较。表中是**逐段绝对差**的均值和最大值，斜线两边分别是帧间隔 2 和 1：

  | | 均值 | 最大值 |
  |---|---|---|
  | 组合奖励 r | 0.007 / 0.007 | 0.033 / 0.019 |
  | 只用 t₀ 系的项的 r | 0.004 / 0.004 | 0.015 / 0.010 |
  | e_loc | 0.004 / 0.004 | 0.018 / 0.020 |

  - 作为比较：组合奖励在真实视频上的均值约为 −0.2；真实视频与冻结视频的奖励差，中位数为 0.28 / 0.17。
  - 逐帧深度 AbsRel：48 帧为 0.060 / 0.058，40 帧为 0.063 / 0.060；两种输入下有效预测比例都是 100%。
  - **结论的适用范围**：在真实视频的 C_b = C_a 设置下，40 帧输入带来的变化远小于"冻结与否"的差别。
  - **尚不能断定**的一点：这个差别相对于同一组生成候选之间的奖励差是否也可以忽略。那要等 S4 测出组内的奖励差异后才能判断。
- **尺度拟合**：60 段全部有效。
- **预测失败与截断**：
  - 所有项都没有出现无效预测（非有限值）。
  - 取到上限 c 的比例：真实视频的 e 和 e_loc 约 0.7–0.9%，d 约 0.3–0.5%；冻结视频的 e 和 e_loc 约 3%。
  - 所以 c = 1 时奖励远未饱和。
- **噪声底**：真实视频、C_b = C_a、40 帧、组合奖励。

  | 帧间隔 | r 均值 | r 范围 | e | d | e_loc |
  |---|---|---|---|---|---|
  | 2 | −0.216 | [−0.63, −0.08] | 0.087 | 0.041 | 0.088 |
  | 1 | −0.193 | [−0.55, −0.07] | 0.082 | 0.029 | 0.082 |

  - 动态点的 e 约为静态点的 1.5–1.7 倍。
  - 不同片段之间的差别很大，所以奖励只宜在**同一组内**比较，这与 GRPO 的组内标准化一致。
- **冻结视频对照（第 0 帧重复 40 次）**：

  | 帧间隔 | 冻结视频奖励更低的片段比例 | 真实与冻结的奖励差（中位数） |
  |---|---|---|
  | 2 | t₀ 系 90% → 组合奖励 93% | 0.100 → 0.279 |
  | 1 | t₀ 系 87% → 组合奖励 93% | 0.070 → 0.166 |

  - 只用 t₀ 系的项时，静态点上的位移误差对冻结视频反而更小。有一段没有动态点、相机移动 1.8 m 的片段，冻结视频的奖励甚至高于真实视频。加入局部项之后，这一段的冻结视频被明确区分出来。
  - 组合奖励下，每个帧间隔仍有 2 段没能区分：
    - `scene_d78_3rd`（约第 3834–3881 帧）：相机几乎不动，冻结视频本来就接近真实，这是预期的；
    - `scene_d78_ego1`（同一时间段）：相机移动 0.07 m，片段中的运动很小。这时 OpenD4RT 在真实视频上的误差，反而大于"一切静止"这个预测。**这是 critic 在低运动片段上的真实弱点。**

**B2 结果：像素约定逐环节量化（2026-09-25）**

脚本：`scripts/b2_pixel_conventions.py`。**这一步只量化偏差，没有改任何接口。**

1. **图像 resize**：
   - 用放在亚像素位置的高斯光斑实测。AnyView 的 PIL LANCZOS、OpenD4RT 训练用的 PIL BILINEAR、推理和 S1 用的 cv2 INTER_AREA，三者都**严格是**像素中心约定：x' = (x + 0.5)·s − 0.5，拟合残差 ≤ 0.003 px。
   - 测了三组尺寸：960×540→576×320、960×540→256²、576×320→256²。
2. **内参**：
   - AnyView 的 `scale_intrinsics` 和 OpenD4RT 的数据 loader 都按乘法缩放（cx·s，没有半像素项）。
   - 所以按内参投影出的位置 s·x，与图像内容的实际位置相差恒定的 0.5·(s − 1) 像素。960→576 时为 −0.20 px，960→256 时为 −0.37 px。
3. **像素到 query**：OpenD4RT 用 `grid_sample(align_corners=True)`，在输入网格上的采样位置是 u·(W_in − 1)。
4. **串起来**（原图宽 960，以 256 网格像素计，"采样位置 − 内容位置"）：
   - OpenD4RT 训练标签（u = s·x/255）：各处都是 +0.37 px，一个**恒定**的偏移，是模型训练时见过的；
   - S1 查询（u = x/(W−1)）：从左边缘的 +0.37 px 线性变到右边缘的 −0.37 px；相对训练约定，右边缘差 0.73 px。y 方向（540→256）约为其 70%。
5. **对奖励的实际影响**：在同样的 30 段、同样的锚点上，比较 S1 约定与训练约定（`scripts/s1_checks.py --query-convention d4rt_train`，帧间隔 2）：
   - 组合奖励逐段绝对差：均值 0.008，最大 0.074（相机几乎不动的 `cnb_dlab_0225_ego2@2505`）。这与 40/48 帧的输入长度扰动（0.007）是同一量级。
   - 训练约定下，逐帧深度 AbsRel 从 0.063 降到 0.058，30 段中 77% 更好；奖励均值从 −0.216 变为 −0.212。
   - 区分冻结视频的能力两者相同：都是 93%，真实与冻结的奖励差中位数为 0.279 与 0.281。
   - 结论：**偏差小于 1 像素，但不能忽略。**证据支持查询改用 OpenD4RT 训练时的约定。
   - **待决定：奖励接口用哪种查询约定**（2026-09-25 提出，尚未决定）。三个选项：
     1. **改用训练约定**：`d4rt_train` 作为默认，S1 以新约定重跑作为基线，`s1` 保留作为对照；生成视频上的查询也用这一约定。依据是深度更准、与模型训练一致。
     2. **等生成侧实测后再定**：先测出 AnyView 生成内容遵循哪种约定（见第 6 点），再选。依据是生成视频中内容的位置未必与真实视频相同。
     3. **保持 `s1`**：视为可忽略。但它与 40/48 帧的扰动同一量级，所以不推荐。
     - **决定（2026-09-25）：真实视频上的检查采用选项 1。** `scripts/s1_checks.py` 的默认改为 `d4rt_train`，`s1` 保留作为对照。§6 S1 已报告的结果仍是 `s1` 约定下的。`d4rt_train` 约定下的基线：
       - 帧间隔 2：见上文第 5 点。
       - 帧间隔 1：组合奖励 −0.187（`s1` 约定为 −0.193），e / d / e_loc 为 0.080 / 0.028 / 0.080；逐帧深度 AbsRel 为 0.056（`s1` 约定为 0.060），30 段中 80% 更好；冻结视频被区分的比例为 93%；40/48 帧组合奖励逐段绝对差的均值为 0.007，最大 0.021。与 `s1` 约定相比，组合奖励逐段绝对差的均值为 0.008，最大 0.067。两种帧间隔的结论一致。
     - **生成视频侧仍待定**：不能只替换归一化公式，要写清完整的转换链：AnyView 输出网格上的图像 → resize 到 256 → 内参如何对应 → 像素坐标怎样转为 query。并用生成视频实测（第 6 点）。
6. **尚未验证**：AnyView 生成的视频中，内容的像素位置究竟遵循哪种约定，取决于模型从训练数据中学到了什么，不能由代码推出。需要在 B1 的基础上实测，例如在 C_b = C_a 时，比较生成视频与输入视频的亚像素平移。

  | SDE a = 0.5 | 11.93 ± 1.22 / 0.399 / 0.621 | +0.28（−0.03 … +0.51） | 16.73 ± 1.02 / 0.521 / 0.473 | +0.17（−1.10 … +2.18） |

- **结论与适用范围**：
  - 35 步下，Euler 和全程 SDE（a ≤ 0.7）相对 AB2 **没有观察到平均指标的下降**。
  - 但每个分割只有 6 个 episode，每种 SDE 设置只抽了一次噪声，逐 episode 的标准差（0.7–1.2 dB）大于均值差。所以**不能据此说 SDE 更好**，也不能据此选定 a。
  - kubric5d 上，SDE 相对 AB2 的变化在不同 episode 之间从 −1.3 到 +2.5 dB。但这是**不同场景之间**的差异，每个场景只生成了一次，所以**不能说明同一场景、同一相机下，不同 seed 的候选之间有足够的差异**，而这才是 GRPO 需要的组内差异。组内差异要固定场景和相机、换多个 seed 来测（见下一步）。
  - C4 中的 log-prob 重算是在 `torch.no_grad()` 下做的，只验证了数值正确性。带梯度的 LoRA 重算（梯度能否到达 LoRA、数值是否一致、反向传播的显存）属于 B5。
  - 指标只衡量与 GT 的像素和感知相似度，不能说明几何一致性。
- **每个 episode 的耗时**：droid 约 173–233 s，kubric5d 约 372–503 s。每个 episode 包含 6 次完整采样，以及前 2 个 episode 的 C3/C4 检查；都是在共享 GPU 上测得。
- **尚未做**：
  - 减少步数（16/12/10）和混合窗口；
  - 每种设置多次抽取噪声，以估计方差；
  - 带梯度的 LoRA 重算，以及它的显存和吞吐（B5）；
  - 生成视频那一侧的像素约定实测。

**B5 结果：带梯度的 LoRA 重算，最小检查与显存（2026-09-25）**

- **实现**：
  - `anyd4rt/anyview_rl/lora.py`：手写 LoRA，包在 28 个 block 的 q/k/v/output 投影和 MLP 两层上，共 280 个无 bias 的线性层。
    - rank 16，alpha 16，共 2294 万个参数。
    - B 初始化为 0。A 的初始化范围与 kaiming_uniform 相同，但用固定 seed 的生成器抽取，以便复现。
    - 基础权重是 bf16 且冻结；LoRA 参数用 fp32，前向时转成输入的精度。
    - 关闭 LoRA 就是参考模型，不需要复制第二份模型。
  - `rollout.step_log_prob`：不加 `no_grad` 的重算，可以在 `torch.enable_grad()` 下把梯度传给 LoRA。`recompute_log_prob` 是它的 no-grad 版本，用于检查。
- **脚本**：`scripts/b5_lora_grad_check.py`。
  - 设置：batch 1，a = 0.7，35 步 SDE rollout（记录每一步）后，检查第 0、17、34 步。
  - 机器：本轮测量时 GPU 没有被其他作业占用（独占 RTX 6000 Ada 48 GB）。
- **正确性**（droid_OOD_LR ep000 和 kubric5d ep000）：

  | 检查 | 结果 |
  |---|---|
  | G1：B = 0 时 LoRA 开 vs 关的 log-prob | 相同，差 0 |
  | G2：带梯度重算 vs no-grad 重算 vs rollout 记录的值 | 三者相同，差 0 |
  | G3：B = 0 时的梯度 | 280 个 B 全部收到有限、非零的梯度；A 的梯度为 0（B = 0 时必然如此） |
  | G3：B 取很小的随机值后的梯度 | 280 个 A 全部收到有限、非零的梯度 |
  | 反向的确定性：同一配置跑两次，比较 B 的完整梯度向量 | 余弦 0.99997，相对 L2 差 0.76%，**不逐位相同** |

  - 前向逐位确定，但 bf16 反向有约 0.8% 的非确定性。这个量级在优化中通常可以接受，但严格复现训练时要记住这一点。
- **显存与耗时**（一次前向 + 反向，batch 1；latent 是 rgb0 的 T×H×W）：

  | 配置 | latent | 峰值已分配显存 | 前向 + 反向 |
  |---|---|---|---|
  | droid（29 帧，576×304），不用激活检查点 | 8×38×72 | 36.4 GiB | 1.8 s |
  | droid，发布版 `mm_only` | 8×38×72 | 34.9 GiB | 2.0 s |
  | droid，本仓库的逐 block 完全重算 | 8×38×72 | **7.0 GiB** | 2.4 s |
  | kubric5d（41 帧），不用检查点或用 `mm_only` | 11×48×72 | OOM（> 47 GB） | — |
  | kubric5d，本仓库的逐 block 完全重算 | 11×48×72 | **9.2 GiB** | 5.4 s |

  - 35 步 rollout 本身：droid 23.4 s，峰值 5.3 GiB；kubric5d 49.6 s，峰值 6.2 GiB。
- **激活检查点**：
  - 显存主要被 28 个 block 为反向保存的激活占用，与 token 数成正比。attention 用的是 SDPA，不会生成完整的注意力矩阵。
  - 发布版的 `sac_mode="block_wise"` 在 torch 2.7 下无法运行：`get_context_fn()` 返回 `None`，报错 `TypeError: 'NoneType' object is not callable`。
  - 所以在本仓库的 `lora.enable_block_checkpoint` 中，用默认上下文（完全重算）包装每个 block，没有改动 AnyView 的代码。
  - 与不用检查点相比：log-prob 逐位相同；梯度的差异与同配置两次运行之间的差异同一量级（余弦 0.99997，相对差 0.74–0.78%），说明重算本身没有引入额外误差。
- **结论**：
  - 带梯度的 LoRA 重算可行：梯度能传到 LoRA，数值与 rollout 一致。
  - 用逐 block 完全重算后，41 帧、576 网格下，**batch = 1、单个去噪步**的一次前向加反向峰值约 9.2 GiB。这**不是**完整 GRPO 更新的显存：完整更新还包括优化器状态、rollout 缓存、参考模型前向和梯度累积，要单独测（见下一步）。
  - §4.6 推算的"约 36 GB"只对应 29 帧、不用检查点的情形，41 帧时不用检查点会超过 47 GB。
- **尚未做**：
  - batch > 1（多个候选一起重算）时的显存与数值；
  - 优化器（AdamW 状态约为 LoRA 参数的 3 倍，只有几百 MB）加上完整一步更新的吞吐；
  - 梯度在 35 步上的累积方式。

**组内差异：同一场景、同一相机，只换 seed（2026-09-25）**

- **脚本**：`scripts/b6_group_diversity.py`。
- **设置**：
  - 数据：droid_OOD_LR 和 kubric5d 各 3 个场景（episode 0–2）。
  - 每个场景 G = 8 个候选，35 步，发布版预处理不变。
  - SDE（a = 0.7）：seed g 同时决定初始噪声和每一步的噪声。
  - AB2：seed g 只决定初始噪声。
- **结果**：

  | 场景 | SDE 相对 GT 的 PSNR（均值 ± 组内标准差，范围） | SDE 候选两两之间的 PSNR / LPIPS | AB2 相对 GT 的 PSNR | AB2 候选两两之间的 PSNR / LPIPS |
  |---|---|---|---|---|
  | droid ep000 | 11.55 ± 0.83（10.03 … 12.73） | 12.52 / 0.586 | 11.31 ± 0.85 | 11.83 / 0.607 |
  | droid ep001 | 10.29 ± 0.41（9.75 … 10.89） | 11.09 / 0.611 | 10.07 ± 0.78 | 10.41 / 0.633 |
  | droid ep002 | 12.05 ± 0.75（11.13 … 13.32） | 12.29 / 0.597 | 11.79 ± 0.59 | 12.21 / 0.597 |
  | kubric5d ep000 | 16.26 ± 0.26（15.86 … 16.64） | 16.84 / 0.455 | 15.96 ± 0.42 | 16.20 / 0.471 |
  | kubric5d ep001 | 17.44 ± 0.20（17.20 … 17.70） | 18.21 / 0.499 | 17.21 ± 0.52 | 17.48 / 0.520 |
  | kubric5d ep002 | 16.70 ± 0.64（15.39 … 17.41） | 18.64 / 0.403 | 16.97 ± 0.50 | 19.06 / 0.422 |

- **观察**：只有 6 个场景，下面都不宜推广。
  - **组内候选确实不同**：
    - 同一场景、同一相机下，候选相对 GT 的 PSNR 组内标准差为 0.2–0.85 dB，droid 上极差达 1.1–2.7 dB。
    - 候选两两之间的 LPIPS（0.40–0.63）与候选相对 GT 的 LPIPS 相当，说明候选之间外观差别很大。
  - **SDE 没有比 AB2 带来更多的组内差异**：
    - PSNR 的组内标准差，SDE 在 6 个场景中有 4 个比 AB2 小；SSIM 和 LPIPS 的标准差也是 4/6。
    - 候选两两之间的 LPIPS，SDE 在 6 个场景中都略低或持平。
    - 结论只到"SDE 没有比 AB2 更多样"为止。这个实验中，SDE 候选的初始噪声和每步噪声同时随 seed 变化，所以**还不能分离初始噪声和逐步噪声各自的贡献**。要分离，需要固定初始噪声、只换每步噪声的 seed，再做一次对照。
  - **平均质量**：SDE 的平均 PSNR 在 6 个场景中有 5 个比 AB2 高 0.2–0.3 dB，kubric5d ep002 上低 0.27 dB。证据不足以说明 SDE 更好。

- **耗时**：每个场景 16 次生成，加上 56 对两两比较。droid 约 8 分钟，kubric5d 约 16.5 分钟（独占 GPU）。

**最小 GRPO 更新检查（2026-09-25，只检查优化器流程）**

- **脚本**：`scripts/b7_grpo_step_check.py`。
- **设置**：
  - 一组 G = 4 个候选，每个候选取 K = 12 个等间隔的去噪步，共 48 项策略重算。
  - 35 步全程 SDE，a = 0.7，LoRA rank 16。
  - AdamW，lr 1e-4，β = 0.01，ε = 1e-4；本仓库的逐 block 完全重算。
- **顺序**（严格同策略，§4.5）：
  1. 先完成 G 次无梯度的 rollout，只缓存选中的步。
  2. 断言从 rollout 开始到累积结束，参数没有变化。
  3. 对每个（候选，去噪步）逐项、batch = 1 地重算：先做参考前向（LoRA 关闭，no-grad），再做策略前向（LoRA 开启，带梯度），接着反向；梯度累积。
  4. 最后统一做一次 `optimizer.step()`。中间不插入原生监督的更新。
- **约束**：`LoRALinear` 在 LoRA 关闭时拒绝带梯度的前向，所以策略前向和它在 checkpoint 反向中的重算不可能在 LoRA 关闭的状态下运行。有单元测试覆盖，包括在前向之后、反向之前关闭 LoRA 的情形。
- **advantage 是人工设定的**：固定值后做标准化。这一步只检查优化器流程，**不能解释为训练收益**。
- **结果**（两个 episode 的检查项全部通过）：

  | | droid_OOD_LR ep000（29 帧，latent 8×38×72） | kubric5d ep000（41 帧，latent 11×48×72） |
  |---|---|---|
  | 从 rollout 到累积结束，参数不变 | 是 | 是 |
  | ρ（同策略时应为 1）/ KL（B = 0 时应为 0） | 48 项全部为 1.0 / 0.0 | 同左 |
  | 梯度有限；梯度范数 | 是；6.2e-4 | 是；5.4e-4 |
  | 更新了的 LoRA 张量比例 | 50%：280 个 B 全部更新；A 的梯度在 B = 0 时为 0，AdamW 不会移动它 | 同左 |
  | 基础权重 | 逐位不变 | 逐位不变 |
  | 保存 LoRA 后，加载到新的 DiT（不同初始化、不用检查点）再采样 | 与更新后的模型输出逐位相同 | 同左 |
  | **整组峰值显存**（模型、缓存、参考与策略前向、带检查点的反向、AdamW） | **7.34 GiB**（缓存 0.61，AdamW 0.17） | **9.62 GiB**（缓存 1.06，AdamW 0.17） |
  | **整组耗时** | 254 s：rollout 98 s，累积 156 s（每项 3.25 s），step 0.1 s | 538 s：rollout 203 s，累积 335 s（每项 7.0 s），step 0.08 s |

- **注意**：更新一步后，缓存步的 log-prob 只改变了约 1e-7，但同一 seed 采样出的 latent 与关闭 LoRA 时最大相差 0.5–0.7。采样轨迹对参数非常敏感。判断一次更新的效果时，应该看 log-prob 和奖励，不能看单条样本。
- 以上测量都是在 GPU 没有被其他作业占用时做的。

### S4 同条件下的奖励排序是否可信

- 每组 G 个候选，除 seed 外所有条件都相同：C_b、Q、参考值、尺度规则、OpenD4RT 快照。
- **组内排序与独立参照的一致性**（Kendall τ）：
  - NVS 数据上用 GT 目标视频；
  - D4RT GT 数据上用"GT 投影 + 第二个重建模型"。
- **重测稳定性**：换一组 query 子集后，排序是否保持。
- 结果不可信时先修正奖励，不进入训练。

**S4 准备与第一轮结果：PointOdyssey 上的几何接口（2026-09-25）**

- **接口**：
  - `anyd4rt/po_episode.py`：把 PointOdyssey 片段转换为 AnyView episode；按 §7.2 构造环绕相机（枢轴取 t₀ 时可见 GT 点的中位点，竖直轴取 C_a(0) 的 y 轴）。
  - `anyd4rt/geometry.py`：`zbuffer`、`zbuffer_visibility`（可见 / 遮挡 / 未知三态）、`orbit_camera`。
- **相机尺度**：PointOdyssey 不在 AnyView 的尺度表里。**暂定 1/8**（表中非驾驶、非 Kubric 数据的默认值），这是 S2 的临时选择。
- **坐标**：
  - 奖励和 z-buffer 始终使用数据集原始世界坐标下的 T_cw。
  - AnyView 收到同样的相机后自行重新锚定，这不会影响奖励（§3.2）。
  - PointOdyssey 的深度图与 GT 点深度一致：可见点的相对误差中位数为 0.7%。
- **生成视频的像素约定（实测）**：
  - 在 θ = 0（C_b = C_a）时，用 phase correlation 比较生成视频与按发布版 LANCZOS（像素中心约定）缩放到同一网格的输入。
  - 3 个场景中所有忠实复现的候选（9 个），亚像素偏移都约为 0.0 px。如果内容遵循乘法缩放的内参，应当偏移 +0.20 / +0.22 px。
  - 所以**生成内容遵循像素中心约定**。生成侧的完整转换链确定为：
    1. 原图像素 x → 网格 x_g = (x + 0.5)·s − 0.5，每个方向分别计算：960×540 → 576×304 时 s = 0.600 / 0.563，是各向异性的；
    2. 网格图像 → cv2 INTER_AREA 缩放到 256²；
    3. query 采用 OpenD4RT 训练约定：u = (256/W_g)·x_g/255。
  - 在 576 网格上，两种映射对奖励的影响只有约 0.001。
- **z-buffer（已修正）**：
  - 第一版取 3×3 邻域的最小深度，结果把深度边缘旁的背景点都判为遮挡：同视角下，GT 可见的点中只有 51% 被判为可见。
  - 改为优先使用点所在格子的深度，格子为空时才用邻域补洞。
  - 修正后在同视角下与 GT `visibs` 对照（3 个场景）：

    | | 结果 |
    |---|---|
    | P(判为可见 \| GT 可见) | 0.75–0.93 |
    | P(判为遮挡 \| GT 遮挡) | 0.56–0.91 |
    | **P(GT 可见 \| 判为可见)** | **0.84–0.93** |

  - 不一致的主要来源是数据本身：
    - 对 GT 可见的点，深度图的深度系统性地比 GT 点深度略小（中位数偏小 0.2–0.9%），其中 5–23% 偏小超过 2%，于是被容差 max(0.05, 0.02z) 判为遮挡；
    - 有 4–21% 的 GT 遮挡点，深度图与 GT 点深度相差不到 2%。
  - 所以 PointOdyssey 的 `visibs` 不完全等同于深度测试。容差暂按 README 原值保留；这意味着 V 中约有 7–16% 的点在目标视角里实际上可能不可见。

    - 排序在两半锚点之间是稳定的（τ = 0.80），所以**排序稳定不等于排序正确**。
- **结论**：
  - 这个奖励能稳定地把塌陷、糊掉的候选排到后面。
  - 但它会把"删除运动主体"排在"主体在场但位置不准"前面。**如果直接用于训练，策略可能学会删除运动物体。**
  - 在正式训练之前需要处理这个漏洞。可能的方向（**尚未实现，待决定**）：
    1. 在动态点上加入"内容是否在场"的检查，例如 §5 的颜色校验，或者 OpenD4RT 的 visibility 输出；
    2. 引入外观一致性，比如与源视频对应 patch 的颜色比较；
    3. 在 S1 中先用物体删除做诊断（A2），量化泄漏率。
  - 以上只来自 3 个场景、2 个角度，每个场景一段片段，不宜推广。
  - **后续诊断（见下一节）修正了这里的判断**：删除之所以胜出，只是在当前聚合方式下的小幅领先；补跑更多 seed 后，有更接近正确的候选高于删除。

**诊断结论**

- **已验证**：
  1. 位移项因为运动信号弱而不起区分作用；
  2. 人物被充分覆盖；
  3. 没有发现尺度或投影的接口错误；
  4. 删除的胜出来自人物点上"露出相近深度的背景"带来的低误差，同时删除候选在静态背景上的几何误差（背景偏 19 px）和画质问题，在当前聚合下被稀释；
  5. 更接近正确的候选（14、11、22）能胜过删除。
- **推测**：
  - 干净的删除能骗过逐点几何误差，这对"背景与物体深度相近"的场景是一种普遍风险；
  - 这次只观察到 24 个样本中的 1 次，是否常见未知。
- **拟采用的最小修改（尚未实现；按用户决定，未设为默认，见下一节的对照实验）**：
  - 奖励改为**静态组与动态组各占一半**；组的划分用 GT 运动，不用掩码；某组为空时只用另一组。
  - 这属于"聚合与权重"层面的修改，是**降低**而不是提高动态部分的比重。
  - 修改后要复测这个案例，并检查其他 5 组的排序是否受损。
  - 同时用上面的像素偏移作为独立参照，计算奖励排序与几何参照之间的 Kendall τ，比较修改前后。
  - 暂不加入外观项。颜色一致性对删除的识别更彻底，但受视角相关的光照和无纹理区域影响，留作后备。

- **假设**：OpenD4RT 在真实源视频上已经预测不准的点，不应直接用于新视角生成的 RL 奖励。源侧可靠不保证目标侧可靠，这需要实验来验证。

  - 之前的实验没有保存视频，所以按原 seed 重新生成。生成是确定性的：cnb_dlab_0215_ego2 θ = 10° 的 8 个候选与 s4b 的奖励逐位相同。

  - 另有 3 个新片段，只取 θ = 10°，每段 8 个 seed。**选片段在看到 A–D 结果之前就定了**，依据是 S1 中的运动幅度和源侧误差：

- **源侧可靠性**（`scripts/s4g_gate_offline.py`）：
  - 在真实源视频上，**只拟合一次尺度**（用所有在源视角 t₀ 可见的锚点）。之后逐轨迹计算 e_i、d_i、e_loc,i，均为该轨迹在源侧可见时刻上的平均。门控之后不再重新拟合。

  - 门控按锚点（GT 点身份）传到目标视角，同组所有候选共享同一个评分集合。
  - 可靠性规则：门控后锚点少于 128 个的组标为不可靠，**不补入低可靠点**。静态、动态各半的聚合在任一组少于 32 个锚点时，退化为只用另一组，并在结果中注明。

  1. 源视角 t₀ 不可见、没有源侧测量：44–279 个（egobody 最多，279 个）；
  2. 源侧误差超过 τ：τ = 0.1 时为 55–831 个，τ = 0.2 时为 7–387 个。

**针对两个问题的检查**

1. **门控之后排序改善，是否只是因为人物或动态点被删光、奖励只剩背景？**
   - 在 r1_new_f 上确实如此（τ = 0.1 时动态锚点只剩 1%），而且与参照的一致性**变差**（背景 0.93 → 0.85，动态 0.71 → 0.50）。
   - 在 egobody_3rd 上也是如此（动态锚点只剩 0%）。它与参照的一致性变好，但参照在这个片段上已经饱和，不可信。
   - 在 ani1_new_ 上是反过来：静态锚点只剩 11%，只剩动态。
   - 在 cnb_dlab_0215_ego2 上，人物点保留了 80–85%，没有被删光，但改善很小。
   - **门控经常整类删除点，使奖励的性质变成"只看背景"或"只看动态"。**
2. **真实源视频上，OpenD4RT 能否恢复人物运动？** 部分能。方向基本正确（余弦 0.81），但幅度只有 GT 的 57–59%。上一节"只是运动小"的说法已经更正。

**结论**

- **门控有没有帮助：在这 6 个 θ = 10° 组上没有稳定的帮助。**
  - cnb_dlab_0215_ego2：略有改善。与目检一致从 23/27 升到 24/27，删除从第 4 名降到第 5 名，稳定性从 0.85 升到 0.90。
  - r1_new_f：变差。
  - ani10_new_f：好坏参半。
  - 新片段：参照不可靠，无法判断。
- **代价**：
  - 保留的锚点比例为 23–91%；
  - 动态点在 3 个场景中被删去 84–100%；
  - 1 个片段在 τ = 0.1 时不可靠。
- **静态、动态各半的聚合（C）**：与 A 基本相同，cnb 上没有改善。上一节 25/27 的近似结论不成立。
- **仍然无法解决的问题**：
  1. 干净的删除在 cnb 上仍然高于人物大致在位的候选（B 中删除排第 5，仍在 seed 4、5 之前）。
  2. OpenD4RT 在真实视频上低估运动，所以位移项对小运动的物体几乎没有约束力。
  3. θ = 10° 时，很多候选整体偏移 10–40 px。当前的像素偏移参照在偏移较大时会饱和，需要更可靠的独立几何参照，才能评估奖励排序。
- **决定**：门控和各半聚合**都不设为默认**，奖励保持配置 A。
- **被门控排除的点**已作为以后 OpenD4RT 在真实源视频上的 GT 难例导出，保存在 `outputs/s4cache/<组>/source_hard_examples.npz`：GT 点身份、源侧 e_i / d_i / e_loc,i、在 τ = 0.1 和 0.2 下被排除的锚点。**不会把原 GT 强加给内容错误的生成视频。**
- 暂不新增外观奖励，不启动正式训练。

### S5 单向训练

- **AnyView（OpenD4RT 冻结），四组对比**：
  1. 相同步数的原生微调；
  2. best-of-G 拒绝采样微调（RAFT）；
  3. GRPO；
  4. GRPO 但去掉位移项；
  5. World-R1 式的自一致奖励：用独立重建模型在生成视频上做重建一致性检查，分别测试加和不加周期解耦。
- **OpenD4RT（AnyView 冻结）**：按 §5 的三组对照。
- **后续消融**：
  - 按时间分段的 advantage 与标量 r 的对比（§3.5）；
  - §5.1(b) 的编辑训练。

### S6 双向迭代与换搭档

- 第 1 轮得到 A₁ 和 D₁。
- 第 2 轮在预算相同的条件下对照：
  - 训练 AnyView 时，分别用 D₀ 和 D₁ 提供奖励；
  - 训练 OpenD4RT 时，分别用 A₀ 和 A₁ 生成的缓存。
- 检验两件事：
  - 更新后的搭档是否比原始搭档更有帮助；
  - 最终模型是否超过同等预算的单向训练。
- **记录奖励随轮次的饱和曲线。** LLM 中的 Meta-Rewarding（2407.19594）发现，只改进生成器时评判能力会很快饱和；这里要检验 critic 用 D₀ 时是否更早饱和、用 D₁ 时是否推迟饱和。
- **合谋检查**：每一轮都要检查 D_k 在 S1 退化测试上的泄漏率。如果泄漏率上升，说明换搭档带来的收益可能来自两者相互迁就，而不是真正变好。

### 评测原则

- **优先使用可用的 GT。** 独立模型只作为辅助参照，**不是真值**；用它之前，要在有 GT 的数据上测出它自身的误差（噪声底）。
- **不自评分**：用于训练的 OpenD4RT 不作为主要裁判。

**AnyView 的评测：**

| 指标类型 | 评测方式 |
|---|---|
| 外观 | AnyViewBench zeroshot（真实数据，Ego-Exo4D 没有像素）和 Kubric5D test 上的 PSNR、SSIM、LPIPS |
| 几何 | 在有 GT 目标视频的数据上，比较同一个独立模型在 V̂_b 和 V_b 上的重建差异 |
| 相机 | 用独立位姿估计器，比较 V̂_b 相对 V_a 的位姿与给定的 C_b |
| 动态轨迹 | 用专门的 2D/3D 跟踪器，先在有 GT 轨迹的数据上校准；VGGT 这类以静态场景为主的模型不适合当裁判 |

- D4RT GT 场景上没有目标 RGB，只能用"GT 投影 + 第二个重建模型"来评测。

**OpenD4RT 的评测：**

- WorldTrack：用仓库自带的 `OD/run_eval_worldtrack.sh`，只用于评测。
- 其他真实数据的深度、位姿、3D 跟踪基准：[待核查] 可用性。

### 7.2 D4RT GT 分支的最小原型配置 [设计]

- **数据**：先用一个数据集（PointOdyssey 或 DynamicReplica）的 train split，每段 41 帧，帧间隔 1 或 2。
- **相机 C_b**：
  - 以 t = 0 时 GT 点的中位点为枢轴 p，以 C_a(0) 的 y 轴为竖直轴；
  - 把整条源轨迹旋转 θ：c_b(t) = p + R_θ(c_a(t) − p)，R_b(t) = R_θ R_a(t)，K_b = K_a；
  - 每组从 θ ∈ {±15°, ±30°} 中取一个，全组共用；
  - 共视覆盖率 < c_min 时换一个 θ，都不满足就跳过这一段。
- **query**：
  - 约一半取动态点、约 20% 取边界点；
  - 时间集 T_e = {0, 4, …, 36}；
  - 按 OpenD4RT 在真实源视频上的误差 e_a(i) 做门控，全组共用。
- **组**：G = 8 个候选，只有 seed 不同。
- **奖励**：
  ```
  r = −[ w_p · Σ_V e / |V| + w_d · Σ_{V_d} d / |V_d| + w_loc · Σ_{V_loc} e_loc / |V_loc| ]
  ```
  - V 和 V_d 的定义见 §3.5，只由 GT 决定，所以分母固定。
  - 无效预测按上限 c 计分。
  - |V_d| = 0 时，去掉第二项；|V_loc| = 0 时，去掉第三项。w_loc 为 [待定]。

### 7.3 仍需决定或解决的问题

1. AnyView 用于 OpenD4RT 数据集的 scale_factor（S2）。
2. 释放的 checkpoint 在 SDE 下的质量、log-prob 重算的正确性，以及 DiT 在 train 和 eval 模式下的一致性（S3）。
3. 40 帧接口（S1）：在真实视频、C_b = C_a 的设置下，40 帧与 48 帧输入的差别很小（组合奖励逐段绝对差的均值为 0.007）。这个差别相对于组内候选之间的差异是否可以忽略，待 S4 确认。40 帧和 48 帧 clip 分开组成 microbatch（§3.4）。
4. 像素约定（B2）：各环节的偏差已经量化（§6 S3 的 B2 结果）。S1 查询与 OpenD4RT 训练约定最多差 0.73 个 256 网格像素，对奖励的影响与 40/48 帧的扰动同一量级；训练约定下深度更准。待定：是否把奖励接口改为训练约定；AnyView 生成内容遵循哪种约定需要实测。
5. 奖励是否可信（S1、S4）；独立评测参照的选择与校准。
6. 在 48 GB 显卡上的 LoRA 显存和吞吐（S3）；GPU 分工：mrtknecht3 的 8 × RTX 6000 Ada 与 HoreKa 的 A100/H100 各承担哪些工作；sshfs 的数据吞吐。
7. squashfs 在计算节点上的挂载，以及各数据集可用的轨迹、可见性和实例掩码（S0）。
8. OpenD4RT 原生损失能否接收字段级掩码；生成视频上 query 的采样方式。
9. 阈值：z_min、N_min、κ、c、δ、ε、β、λ_nat、β_g、τ_ph、c_min、w_p、w_d。
10. 数据泄漏检查：AnyViewBench indist 与 Kubric5D_train 是否重叠。
11. NVS 分支：尺度方案 A 与 B 的选择，以及退化判据。
12. 后续可选：§5.1(b) 可控三维场景的重新渲染是否可行（Kubric 场景文件）。
13. 后续可选：§3.5 的分段 advantage 相对标量 r 是否有收益；它不解决扩散去噪步上的信用分配。
14. AnyView 重新锚定变换 `T_anchor` 的保存和单元测试（§3.2）。
